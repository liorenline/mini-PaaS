# Модель загроз

Документ описує, від чого mini-PaaS захищає, а від чого поки ні. Він оновлюється з кожною версією.

**Версія моделі:** v0 · для платформи `v0.1.x`

## Контекст

Зараз платформа працює на локальній віртуалці (Vagrant + UTM на Mac) і має одного користувача: я одночасно і оператор платформи, і розробник застосунків. Платформа не доступна з інтернету.

Ця модель описує поточний стан чесно, разом зі слабкими місцями. Мета наступних версій — закрити ризики зі списку нижче.

## Що захищаємо

| Актив | Чому важливо |
|---|---|
| Сервер платформи (віртуалка) | Якщо його захоплено, захоплено все: усі застосунки і сама платформа |
| Скрипти платформи (`platform/`) | Виконуються при кожному деплої; підміна скрипта = виконання чужого коду |
| Код і дані застосунків | Застосунки не мають читати чи змінювати один одного |
| SSH-ключі | Дають повний доступ до сервера і права на деплой |
| Mac-хост | Папка проєкту спільна з віртуалкою через `/vagrant` |
| Доступність | Один застосунок не має покласти інші чи весь сервер |

## Від кого захищаємо

1. **Шкідливий або зламаний застосунок.** Платформа за своєю суттю запускає чужий код. Застосунок може бути зламаний через вразливість або бути шкідливим від початку. Це головна загроза для будь-якого PaaS.
2. **Шкідлива залежність (supply chain).** `npm install` завантажує пакети з інтернету, і вони можуть виконати код ще під час встановлення (`postinstall`).
3. **Витік облікових даних.** SSH-ключ, токен чи пароль, що потрапили в git або в логи. Це вже ставалося: SSH-ключ віртуалки потрапив в історію репозиторію.
4. **Зовнішній атакувальник у мережі.** Зараз ризик низький, бо віртуалка локальна, але стане головним після переїзду в хмару.
5. **Помилка оператора.** Неправильний порт, зламаний скрипт, деплой не того коду.

## Точки входу

| Точка входу | Хто має доступ | Що відбувається |
|---|---|---|
| **SSH (порт 22)** | Власник SSH-ключа | Повний shell на сервері від користувача `vagrant` (має sudo без пароля) |
| **`git push`** | Власник SSH-ключа (працює через SSH) | Хук `post-receive` запускає `deploy.sh`: код копіюється, виконується `npm install`, стартує systemd-сервіс |
| **Порти застосунків** | Будь-хто, хто бачить мережу віртуалки | Прямий HTTP-доступ до застосунку, без TLS і без проксі |
| **Спільна папка `/vagrant`** | Будь-який процес на віртуалці з правами на запис | Пряма зміна файлів у папці проєкту на Mac, зокрема скриптів платформи |
| **Python CLI** | Користувач на Mac | Виконує команди на сервері через SSH |

## Що вже зроблено

- Скомпрометований SSH-ключ віртуалки замінено (`vagrant destroy` + `vagrant up`)
- `gitleaks` перевіряє кожен коміт локально (pre-commit) і всю історію в CI
- `ShellCheck` і `Ruff` у CI ловлять помилки у скриптах платформи та CLI
- `create-app.sh` і `deploy.sh` перевіряють назву застосунку, порт і дублікати
- Health check після деплою

## Поза межами цієї моделі

- Захист самого Mac-хоста і облікового запису GitHub
- Фізичний доступ до комп'ютера
- Багатокористувацький режим (поки є лише один користувач)
- Вразливості в коді самих застосунків (відповідальність розробника; платформа лише шукає відомі CVE, починаючи з v0.2)
